# 시스템 아키텍처

## 1. 개요
E-FairBoard는 종이 포스터/팜플렛을 e-Paper로 대체하고, 여러 게시판을 중앙에서 한 번에
업데이트하는 저전력 무선 안내 시스템이다. 관리자는 웹 대시보드에서 콘텐츠를 작성·예약하고,
LoRa 게이트웨이가 각 노드에 변경분만 전송한다. 노드는 e-Paper로 표시하고 갱신 성공/배터리
상태를 보고한다.

시스템은 세 축으로 나뉜다 — **웹(서버+대시보드)**, **모듈 펌웨어(게이트웨이·노드)**,
**하드웨어(배선·전원)**. 세 축의 접점은 두 개의 계약 문서로 고정한다: 무선/시리얼
규약은 [PROTOCOL.md](PROTOCOL.md), 부품·핀맵·전원은 [HARDWARE.md](HARDWARE.md).

## 2. 토폴로지
```
[Vue 대시보드] ─HTTP─ [FastAPI 서버(노트북)] ─USB Serial─ [ESP32 게이트웨이 +Core1262]
                                                                   │ LoRa 920MHz
                       ┌───────────────────────────┬───────────────┘
                 [노드1 ESP32+Core1262+ePaper] [노드2 ESP32+Core1262+ePaper]
                  배터리/딥슬립, QR 온디바이스 렌더, ACK 보고
```
- NodeID: `0x00`=게이트웨이, `0x01~0xFE`=노드, `0xFF`=브로드캐스트
- 게이트웨이가 마스터, 노드는 요청에 응답.
- 하드웨어 도착 전에는 서버가 **가상 게이트웨이·가상 노드 시뮬레이터**로 위 토폴로지를
  그대로 재현한다(transport 계층만 교체). 이 부분은 이미 구현되어 있다(`server/backend`).

## 3. 구성요소
### 3.1 웹 — 중앙 관리 서버 + 대시보드 (server/, 우진)
- 관리자 웹 대시보드(Vue 3), 게시물 작성/수정/삭제/예약
- 노드별·그룹별 콘텐츠 배포, 템플릿 선택, QR URL 관리
- 종이 절감량·업데이트 성공률·노드 배터리 시각화, e-Paper 가상 미리보기
- 게이트웨이와 USB 시리얼 브리지(pyserial), 프로토콜 계층(패킷·CRC·COBS·재전송) 구현
- 하드웨어 부재 시 가상 노드 시뮬레이터로 전 기능 동작(`TRANSPORT_MODE=virtual|serial`)

### 3.2 모듈 펌웨어 — LoRa 게이트웨이 (gateway/, 준표)
- ESP32 + Core1262(SX1262)
- 서버↔LoRa 변환, 노드 주소 관리, 재전송, ACK 수집
- 서버 연결은 USB 시리얼(MVP)

### 3.3 모듈 펌웨어 — e-Paper 노드 (node/, 준표)
- ESP32 + Core1262 + e-Paper 2.9"
- 콘텐츠 수신·CRC 검증·로컬 저장(LittleFS)·화면 갱신·배터리 보고
- 평상시 딥슬립, QR은 노드가 직접 렌더

### 3.4 하드웨어 — 배선·전원 (효민)
- 게이트웨이·노드 물리 조립, 공유 SPI 버스 결선, 핀맵 검증([HARDWARE.md](HARDWARE.md))
- 전원 회로: 18650 + TP4056 충전 + MT3608 부스트, LoRa TX 돌입전류 디커플링
- 저전력: 딥슬립 전류 측정·최적화(“1회 충전 2주” 목표 검증)

## 4. 기술 스택
| 영역 | 선택 |
|------|------|
| 웹 백엔드 | FastAPI + APScheduler + pyserial, 메모리+JSON 상태(DB 없음) |
| 웹 프론트 | Vue 3 + Vite + TypeScript + Pinia + Element Plus + Chart.js |
| 펌웨어 빌드 | PlatformIO + ESP32 Arduino core |
| LoRa | RadioLib (SX1262 / Core1262 SPI) |
| e-Paper | GxEPD2 + Adafruit_GFX (부분갱신) |
| QR | ricmoo/QRCode (온디바이스 렌더) |
| 저전력/저장 | esp_deep_sleep + LittleFS |

## 5. 역할 분담
| 담당 | 브랜치 | 영역 |
|------|------|------|
| 우진(팀장) | `wj` | **웹 전체** — 프론트엔드 + 백엔드(FastAPI 서버·대시보드·시리얼 브리지·가상 시뮬레이터) |
| 준표 | `jp` | **모듈 펌웨어 코딩 + 프로토콜 스펙 주관** — LoRa 게이트웨이 + e-Paper 노드(RadioLib·GxEPD2·QR·딥슬립), [PROTOCOL.md](PROTOCOL.md) 관리 |
| 효민 | `hm` | **하드웨어** — 배선·SPI 결선·전원 관리(배터리·충전·부스트·딥슬립 전류) |

- **프로토콜([PROTOCOL.md](PROTOCOL.md))은 웹·펌웨어 공통 계약이며 주관은 준표.** 스펙 변경·버전
  관리는 준표가 맡고, 우진은 서버 측 레퍼런스 구현(`server/backend/app/protocol`, 테스트 벡터 포함)으로
  이를 구현·상호 검증한다.
- **하드웨어([HARDWARE.md](HARDWARE.md))는 펌웨어·하드웨어 공통 계약.** 효민이 배선·전원을,
  준표가 그 위에서 펌웨어를 올린다.

## 6. MVP 범위
텍스트 + QR / 2노드 / 일괄·개별 배포 / ACK·재전송 / 배터리 보고.
서버 상태는 **메모리+JSON**(DB 없음). 하드웨어 도착 전 웹은 가상 시뮬레이터로 완성.
이미지 분할 전송, Wi-Fi 게이트웨이, SQLite 시계열 이력은 스트레치.

## 7. 정량 목표
- 2개 노드 동시 제어(일괄·개별)
- LoRa 통신 성공률 95% 이상
- 텍스트/QR 공지 업데이트 30초 이내
- 노드 1회 충전 2주 이상(저전력 보드 기준)
- 종이 팜플렛 100장 이상 대체 시나리오
